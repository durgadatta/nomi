## Executive Verdict

Nomi is now a credible language laboratory. It has a coherent cognitive
thesis, a substantial cross-language evidence base, a working Python-hosted
runtime, a browser-default Rust/WASM-to-JavaScript path, a notebook kernel,
versioned Core IR contracts, and a healthy test suite.

It is not yet a coherent first product.

The primary risk is no longer lack of ideas or weak engineering. The risk is
**failure to close a user-visible semantic loop before opening the next one**.
The repository currently has more mature research, convenience syntax, passive
metadata, and target programs than it has end-to-end everyday workflows.

The current shape is roughly:

```text
design coherence       strong
test/infrastructure    strong
syntax breadth         broad
first-hour experience  partial
data-boundary utility  mostly target-only
explanation UX         record shapes without a complete user view
industrial readiness  intentionally early
```

The next milestone should therefore not be another broad feature family. It
should be:

```text
one trustworthy first hour
-> one real checked data boundary
-> one boring useful program
-> one shared explanation view
```

Only after that loop is real across CLI, web, notebook, and tests should the
project resume broad match, table-plan, block-policy, capability, symbolic, or
new parser work.

## Review Standard

The project goal combines two different qualities:

| Quality | Operational meaning |
| --- | --- |
| User friendly | A new user can write, run, understand, and repair a useful program without learning Nomi's research history or implementation architecture. |
| Industrial scale | Semantics, diagnostics, modules, packages, tooling, compatibility, security, performance, and releases are explicit contracts rather than conventions hidden in one runtime. |

Industrial scale does not mean implementing every ambitious feature. It means
that a small supported language can be trusted, evolved, and operated at
scale. Nomi should first become narrow and trustworthy, then broad and
powerful.

## What Is Strong

### 1. The cognitive spine is genuinely coherent

The sequence in
[`language_foundation.md`](../language/language_foundation.md) is memorable:

```text
name -> judge -> transform -> choose -> group -> repeat -> sequence
-> touch the world -> explain
```

The corresponding normal forms give the project a real admission test:
binding, function, pattern, flow, block, absence/result, data boundary, and
explanation. This is much stronger than a catalogue of borrowed syntax.

### 2. The implementation has useful seams

Feature manifests, Surface nodes, Core IR, runtime sessions, versioned JSON
contracts, backend capability records, structured execution results, and
semantic events are all appropriate foundations for an exploratory language.
The project has avoided making one parser or runtime the declared language
definition.

### 3. Validation quality is unusually good for this stage

The test suite covers parser behavior, desugaring, three interpreter modes,
runtime contracts, backend fixtures, CLI, notebook behavior, and browser
contracts. Generated web artifacts also have freshness checks. This provides a
strong base for making sharper semantic changes.

### 4. Target programs are grounded enough to apply pressure

[`serious_language_target_demo.nomi`](../language/serious_language_target_demo.nomi)
is valuable as a north-star fixture. It tests whether data, boundaries,
tables, units, symbolic work, world capabilities, services, and explanation
can feel like one language. It should remain a pressure reservoir, not be
treated as an implementation checklist.

### 5. More comparative research is not currently needed

The existing research corpus already covers the relevant language families,
tooling surfaces, data systems, diagnostics, packaging, security, notebooks,
and pedagogy. The next learning should come from users and executable Nomi
programs.

## Critical Findings

### P0. The milestone order is inverted

The canonical foundation says Milestone 1 includes:

- shared assignment and parameter constraint semantics;
- a structured `BindingError`;
- source spans in diagnostics;
- success and failure tests.

The implementation has completed the shared metadata and tentative-commit
parts, but the user-facing closure is unfinished. Despite that, the current
operational queue moves next to passive match captures, flow metadata,
collection plans, block-policy metadata, and capability records.

That sequence is architecturally defensible but product-incomplete. It permits
many good commits without improving the experience of one ordinary user.

**Recommendation:** keep completed operational slices 1-5, but insert a
first-hour closure phase and a real decode phase before current slice 6.

### P0. Nomi's first differentiator is not delivered end to end

The first-hour promise is "checked local meaning with helpful diagnostics."
The runtime already produces a useful binding message and
`NOMI-BINDING-CONSTRAINT`, but the inspected result still has:

```text
span: None
source_excerpt: None
details.constraint_expr: None
```

The rule survives inside the rendered aggregate message, but not reliably as
structured data. This weakens terminal rendering, editor highlighting,
notebook display, web display, tests, and future agent tooling.

The frontends then dilute the structured contract further:

- [`scripts/cli.py`](../../scripts/cli.py) prints banners and every global
  binding after a normal run. Function values expose Python implementation
  representations and memory addresses. Structured diagnostic rendering is
  absent.
- [`web/runtime.js`](../../web/runtime.js) displays `result.error` or plain
  output and does not render the diagnostics array as the primary error view.
- [`tools/jupyter/nomi_kernel.py`](../../tools/jupyter/nomi_kernel.py) still
  carries `NOMI-ARCH-024` for shared diagnostics/events.
- [`first_hour_nomi.md`](../language/first_hour_nomi.md) is an active teaching
  plan, not a runnable tutorial.

The web quick tour also begins with equations, underscore lambdas, pipelines,
and inline match. Those are attractive later forms, but the first-hour plan
explicitly excludes pipelines and match and says ordinary `func` should be the
initial function story.

### P0. Some truth surfaces verify the wrong artifact

On `samples/demo_terse.nomi`, the fresh review observed:

- `--stage core-verify` reports `PASS` and shows three separate `label`
  bindings from the piecewise equations;
- `--stage core-json` shows the executable session result: one `label`
  function with match dispatch.

The cause is visible in
[`prototype/runtime/api.py`](../../prototype/runtime/api.py): several Core
inspection stages parse and lower directly, while `core-json` goes through
`RuntimeSession` and its session lowerer/desugar pipeline. The first artifact
is structurally valid Core IR, but it is not the same semantic program the
default session executes.

For a language that promises inspectable reduction, "verified" must mean the
executable lowered artifact, or the stage must be explicitly named
`pre-desugar-core`.

The capability matrix has a related ambiguity. All feature rows report
`web=no` and `notebook=no`, even though the browser quick tour runs and the
notebook has executable coverage. Conservative `no` is safer than optimistic
`yes`, but a boolean cannot distinguish:

```text
unsupported | not declared | partial | fixture-proven | fully supported
```

### P1. The default surface is ahead of the semantic core

The current feature manifest has 28 non-target rows. Twenty-three are L4 sugar
rows. Some rows are implementation pieces of the same user feature, so this is
not a count of 23 independent language ideas, but it still reveals the current
investment pattern.

Nomi already implements piecewise functions, where clauses, underscore
lambdas, positional holes, unless, postfix conditionals, implicit
multiplication, if-let, try expressions, match expressions, composition,
defer, function equations, sections, and other reductions. At the same time,
the following central promises remain incomplete:

- source-spanned first-hour diagnostics;
- real `Data.decode` behavior;
- `Result` as an everyday expected-failure path;
- a small standard prelude for boring tasks;
- one user-visible `explain` renderer;
- consistent frontend capability claims.

This is the opposite of the desired cognitive order: semantic depth should
earn convenience breadth.

**Recommendation:** freeze new default syntax. Keep existing syntax stable for
compatibility, but teach one canonical path and classify later conveniences by
profile or lesson stage before adding more.

### P1. The data boundary is still a record skeleton, not useful behavior

[`data_decode_boundary_feature.md`](../features/data_decode_boundary_feature.md)
has a strong design and
[`prototype/runtime/decode.py`](../../prototype/runtime/decode.py) has good
passive error records. There is no real `Data.decode` helper in the runtime,
however. Current `data` behavior is still closer to generated class/record
semantics than to the promised transition from external representation to
owned meaning.

This is the most important missing everyday capability. It is where Nomi can
be visibly better than Python without requiring advanced syntax.

### P1. Frontend and backend diversity is growing faster than semantic authority

Nomi has two real execution roads:

```text
Lark -> Python AST -> layered interpreter
Rust/WASM AST payload -> JavaScript lowering -> Core IR -> JS runtime
```

That is useful experimentation, but it means each new feature can acquire two
lowerings, two diagnostic paths, and two failure behaviors. The parser registry
also advertises several additional research candidates.

The project needs one authoritative Nomi-owned Surface-to-Core contract before
feature breadth grows much further. Parser frontends should compete on how
well they produce that contract, not become parallel semantic
implementations.

### P1. The product story is not yet singular

The root [`README.md`](../../README.md) still frames the core primarily as
variables, functions, applications, and Lambda Calculus. The active foundation
defines a richer human core of binding, constraints, data, patterns, flow,
blocks, boundaries, and explanation. Both are valuable, but they currently
sound like different product stories.

There is also a concrete syntax mismatch: the string design declares
f-strings as the one interpolation mechanism, while the first-hour examples
use `"Hello, {name}"` without the `f` prefix.

These inconsistencies are small in code and large in teaching. A cognitively
friendly language needs one first explanation, one first function form, one
interpolation form, and one first error story.

### P2. Industrial work is planned but not yet productized

The repository does not yet have the usual release and ecosystem contracts:
canonical formatting, a language server, stable module/package behavior,
compatibility or edition policy, CI configuration, release metadata, or a
declared security/performance envelope. This is reasonable for an early
language lab. It becomes a problem only if broad language features are called
"industrial scale" before these contracts exist.

Industrialization should be a gated program after the first useful semantic
core, not a simultaneous expansion across every ambition in the serious target
demo.

## Reordered Action Plan

This is the concrete recommended order. It intentionally supersedes only the
*ordering* of the current operational queue. The completed substrate work
remains valuable.

### Gate A: Trustworthy First Hour

| Order | Action | Primary artifacts | Completion gate |
| --- | --- | --- | --- |
| A1 | Freeze new default syntax and parser candidates during the closure phase. | `implementation_todos.md`, feature manifests | Every active commit closes binding/diagnostic/frontend behavior or fixes truth surfaces. |
| A2 | Make Core inspection follow the executable session lowering path. Keep a separately named pre-desugar stage only if it is useful. | `prototype/runtime/api.py`, `tools/syntax/inspect.py`, runtime inspection tests | `core`, `core-verify`, and `core-json` agree on the reduced piecewise-function shape; a regression test proves it. |
| A3 | Preserve source spans and individual failed rules through `Constraint`, `BindingTarget`, `BindingError`, aggregate failures, diagnostics, and events. | `prototype/syntax/surface.py`, `prototype/interpreter/nomi/binding.py`, `prototype/runtime/diagnostics.py` | A failed constrained binding reports file/cell, line/column, excerpt, value, exact rule, human message, binding role, and next step as structured fields. |
| A4 | Turn the CLI into a normal product surface. Print program output by default, move environment dumping behind `--inspect-bindings`, render structured diagnostics, suppress Python tracebacks for ordinary language failures, and return a nonzero exit status. | `scripts/cli.py`, CLI e2e tests | Successful output is clean; expected Nomi failures have one concise diagnostic; debug details are opt-in. |
| A5 | Make web and notebook consume the same result contract. Add a shared record serializer/renderer contract rather than parallel strings. | `prototype/runtime/api.py`, `prototype/runtime/js/worker.js`, `web/runtime.js`, `tools/jupyter/nomi_kernel.py` | One invalid binding fixture produces the same diagnostic code and semantic fields in CLI, web, and notebook tests. |
| A6 | Ship a runnable first-hour ladder using only canonical syntax: values, names, calls, `func`, f-strings, one constraint, and one intentional failure. | `docs/language/first_hour_nomi.md`, a tested `samples/` file, web demo list, notebook tour | The same source is runnable in default, reduced, browser, and notebook/session paths; snapshots and docs agree. |
| A7 | Refresh capability truth from evidence. Replace ambiguous booleans where necessary with `unsupported`, `undeclared`, `partial`, or `proven`, scoped by pipeline/frontend. | `prototype/syntax/features.py`, capability inspection, `current_capability_matrix.md` | First-hour features have explicit CLI/web/notebook evidence; unknown and unsupported are distinguishable. |

Gate A is complete only when a new user can run the first-hour program, make a
constraint mistake, understand the error, and see the same meaning in every
supported frontend.

### Gate B: First Boring Useful Program

| Order | Action | Primary artifacts | Completion gate |
| --- | --- | --- | --- |
| B1 | Implement the minimum everyday `Result` representation needed by decode. Do not add propagation sugar yet. | absence/result feature docs, runtime values, pattern tests | `Ok(value)` and `Err(error)` construct, display, and match consistently across supported runtimes. |
| B2 | Implement `Data.decode` for in-memory mappings before files or network. Reuse the binding engine and accumulate field errors. | `data_decode_boundary_feature.md`, data runtime/lowering, decode tests | Required/default/extra/nested fields, constraints, field paths, source identity, and redaction have focused success and failure tests. |
| B3 | Build the smallest pure prelude needed for one ordinary task. Start with text, mapping/list flow, and JSON-like values; add world capabilities only when the task needs them. | `prelude_and_standard_library_plan.md`, host capability manifest, prelude modules | The task does not depend on private Python imports or browser-only shims. |
| B4 | Add one boring conformance program: decode configuration plus records, transform a collection, and report accepted/rejected values. | target fixture promoted to `samples/` only after support exists | The program runs through Python/session and browser/Core paths with equivalent output and diagnostics. |
| B5 | Render `explain` for binding and decode events only. Grow producer families after the first view is useful. | `explanation_trace_feature.md`, terminal/web/notebook renderers | `explain` answers what, where, value, rule, repair, and redaction for the conformance program. |

Gate B is the first serious product proof. It should be demonstrably easier to
debug than the equivalent Python dictionary plus manual-validation program.

### Gate C: Resume Semantic Breadth

After Gates A and B, resume the active implementation sequence with one rule:
passive representation and real user behavior must land close together.

1. Prepare match captures for shared `BindingTarget`, then immediately prove a
   constrained capture and distinct non-match/constraint diagnostics.
2. Add `FlowStep`, then immediately trace one real canonical collection flow.
3. Add a passive `CollectionPlan` only when one runnable table operation can
   create and explain it. Do not add `query:` syntax yet.
4. Add `BlockPolicy` metadata, then immediately instrument one already-working
   block policy through enter/yield/resume/cleanup.
5. Add capability grant/denial records only alongside an enforceable host
   boundary.
6. Refresh frontend capability evidence after each vertical slice.

Symbolic rewrite, dense array/rank notation, scoped notation, advanced
concurrency, and new parser candidates should remain target/research work until
these normal forms are complete.

### Gate D: Industrial Foundation

Begin this gate only after Nomi has stable first-hour and boring-task programs.
The work should proceed in dependency order:

1. **Canonical semantic pipeline:** versioned Nomi Surface IR with source spans,
   one authoritative lowering to verified Core IR, and backend conformance
   fixtures.
2. **Formatter:** one canonical, no-configuration formatter covering every
   default syntax form and preserving comments.
3. **Modules and Python interop:** explicit import/export behavior, package
   layout, foreign-value boundaries, and diagnostic ownership.
4. **Package and compatibility model:** manifests, locked dependencies,
   integrity, supported runtime versions, deprecation rules, and editions or
   equivalent migration policy.
5. **Language server:** diagnostics, symbols, hover, go-to-definition, and
   formatting driven by the same parser and result contracts as execution.
6. **Release engineering:** CI on supported platforms, deterministic builds,
   license and package metadata, changelog, release artifacts, and conformance
   suite.
7. **Operational quality:** performance budgets, cancellation, resource limits,
   capability enforcement, secret redaction, supply-chain policy, fuzzing, and
   crash diagnostics.

Do not start all seven tracks in parallel. Each should reuse the semantic
artifacts proven by the previous gate.

## What To Stop Doing For Now

- Do not start more broad comparative research.
- Do not add another whole-project synthesis or roadmap.
- Do not add new default syntax before the first-hour and decode gates close.
- Do not add more parser frontend candidates before Surface/Core authority is
  clear.
- Do not promote target-only code from the serious demo into `samples/` to make
  the project appear more complete.
- Do not count passive records as finished features until one user path
  consumes them.
- Do not equate a large passing test count with language-product completeness.

## Success Measures

Use a small set of product measures rather than feature count:

| Measure | Near-term target |
| --- | --- |
| First useful program | One command or one playground action, no setup theory. |
| Diagnostic completeness | Every first-hour semantic failure has source, value, rule, repair, and redaction fields. |
| Frontend parity | Shared conformance fixtures report equivalent value/output/diagnostic semantics across declared pipelines. |
| Capability honesty | Every `yes` or `proven` claim names the test or fixture that proves it. |
| Semantic closure | Every new passive record is consumed by a real behavior path within the same milestone. |
| Cognitive surface | The first tutorial teaches one path; later sugar is clearly staged rather than presented as a menu. |
| Industrial progress | Formatter, module/package, LSP, compatibility, release, security, and performance gates are tracked independently of syntax breadth. |

## Bottom Line

Nomi does not need a larger vision. It needs a smaller finish line.

The project should preserve its long-range ambition, keep the serious target
demo, and continue building a replaceable semantic substrate. But the next
proof of progress should be human: a new user writes a small program, crosses a
checked data boundary, makes a mistake, understands the explanation, and gets
the same answer in every supported environment.

That is both the cognitive-language milestone and the first real step toward
industrial scale.
